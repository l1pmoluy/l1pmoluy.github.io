APC/DPC

APC

线程异步回调
让一段代码在指定线程的上下文中被异步执行

流程

结构简述

每个线程里有APC状态结构

ApcListHead中包含的是
0 KernelAPC
1 UserAPC
所以每个APC环境中分两个队列，KernelAPC List 和 UserAPC List
这里的队列节点就是常用的KAPC，并呈现双向链表结构

在队列中，排在前面的部分的是没有 NormalRoutine 的 KAPC
然后是有 NormalRoutine 的KAPC，这里 NormalRoutine 是一个函数，会在 KernelRoutine 函数运行后调用
同时KAPC中还包含一个环境的变量 ApcStateIndex 来说明的是当前KAPC处于什么环境
这里需要回到开头，线程中的APC状态结构有
KAPC_STATE ApcState;
KAPC_STATE SavedApcState;
如果说 线程1 挂靠到别的进程中，那么 ApcStateIndex 负责说明，该APC属于那种环境，也就是上述两种KAPC_STATE的哪个
举例：没有挂靠时
ApcState → 1.exe APC队列
SavedApcState → 未使用
挂靠时
SavedApcState = 新线程APC队列
SavedApcState → 1.exe APC队列

把中断处理里耗时的工作延迟到稍后执行，从而让中断处理函数尽快返回

流程

ISR的作用是1.确认终端 2.读取关键数据 3.排队一个DPC

缩写 全称 含义
APC Asynchronous Procedure Call 异步过程调用，允许在用户模式或内核模式线程上下文中延迟执行一个函数
DPC Deferred Procedure Call 延迟过程调用，只能在内核模式 IRQL ≤ DISPATCH_LEVEL 上执行，通常用于中断服务程序延迟处理
特性 APC DPC
— — —
执行模式 用户模式或内核模式 内核模式
调用上下文 特定线程的上下文（Thread Context） 中断上下文（Interrupt Context）或 DISPATCH_LEVEL
队列位置 每个线程有自己的 APC 队列 每个处理器有自己的 DPC 队列
延迟原因 延迟执行某个线程的操作 延迟 ISR（中断服务程序）不应在高 IRQL 做长时间操作的处理

寄存器 存的什么

CR2 最近一次缺页的虚拟地址（#PF 时硬件自动填）

CR4 扩展功能开关排（VMXE 在这）
CR8 中断优先级（TPR）

API

KeGenericCallDpc(Routine, Context)—— 发起端 向系统里的每个处理器各排一个 DPC，并等待所有 CPU 都执行完才返回。你在主线程里调用它，Routine 就会在每个 CPU 的 DISPATCH_LEVEL 上被同时调起来。Context 会作为 DeferredContext 传给 DPC 例程。
KeSignalCallDpcSynchronize(SystemArgument2)—— DPC 内的“栅栏” 在 DPC 例程内部调用。它表示“我这个 CPU 已经到了同步点”，然后阻塞等待所有其他 CPU 也到达这一点。返回值是 LOGICAL：最后一个到达栅栏的 CPU 得到 TRUE，其余得到 FALSE（可以用它判断“我是不是最后一个”，好做清理工作）。
KeSignalCallDpcDone(SystemArgument1) —— DPC 内的“完成信号” 也在 DPC 例程内部调用，表示“我这个 CPU 干完了”。最后一个 CPU 调用它之后，发起端的 KeGenericCallDpc 才解除等待返回。

VMON 一块至少一个页的内存
​
x64 CPU 在 VT 概念里有两层运行模式：
  • VMX root 操作模式 ：全权模式，hypervisor（你的驱动）跑在这里，能看能管一切；
  • VMX non-root 模式 ：受限模式，被虚拟化的对象（guest）跑在这里，敏感指令会触发 VM-exit 退回 root 模式。
    VMXON指令的作用就是：把当前这个 CPU 切进 VMX root 模式，同时给 CPU 注册一块“VMXON region”内存让芯片存 VMX 内部状态。注意两点：
  1. VMXON 执行完 ，Windows 本身还在这个 CPU 上正常跑（只是变成了跑在 root 模式），系统毫无感觉；
  2. VMXON ≠ 虚拟化开始。它只是“开门”，真正的 guest 要等你下一步搞完 VMCS 再用 VMLAUNCH 拉起来。

线性地址对应物理地址

假如我在记事本中写了一串字符”helloworld”，然后用工具比如CE查找到该字符串在内存中的地址00484C58那么可以按照10-10-12的方式解析该虚拟地址的物理地址，所谓101012就是bit位排布，首先把000AE928换成二进制bit位形式0000 0000 0100 1000 0100 1100 0101 1000，然后划分
10 00 0000 0001 1 页目录 单位14byte PDE
10 00 1000 0100 84 页表项 单位14byte PTE
12 1100 0101 1000 C58 页内偏移 单位1byte
于是就可以找物理地址了，于是就弥补了前文的无知，cr3是什么？cr3就是改进程(书)地址的寄存器，代表了该书，用! process 0 0列举所有cr3的值找到notepad.exe，得到物理基地址03d75000
! dd 03d75000来获取目录物理地址的值，目录中存放的是指针，也不难想到指针指向的地方就是书本内容的地方，比如这个要找的就是! dd 03d75000+14->3cbc7867，这里要去掉867，这个是页属性得到3cbc7000，这就是当前页的起始地址，再接着加上844，得到3d25b867，同理3d25b000，于是就可以看里面的内容了

映射节、事务与回滚

映射节

对于物理内存，我们可以映射出内存，如果这个文件需要被很多文件使用，那么映射出来的内存理应可以被共享——共享节
如一个dll，加载到内存模块中，便是创建了一个映射，CreateSection，对应的我们也可以通过MapViewFile来观察到共享空间，且改变共享空间以至于改变物理地址文件
这里涉及到的API有，我们按照api讲述
NtCreateSection/CreateFileMapping
OpenFileMapping
MapViewOfFile
Unmap
Remap
先说创建，创建Section，实际上是将物理内存映射在内存中，返回一个句柄
再说打开，映射在内存中之后，若有别的进程的程序想要访问此Section，就可以通过OpenFIleMapping打开该Section并返回句柄
MapViewOfFile，映射成功后，用该API得到虚拟基地址
Unmap，解除该Section，注意，解除后不代表进程消失
Remap，重定向这片Section，可以自己再创建一个，并重定向原本映射的节区

事务 | 回滚

事务（Transaction）： Windows 提供的事务机制称 Kernel Transaction Manager（KTM），文件级实现叫 TxF（Transactional NTFS）。
回滚（Rollback）：当事务中某步失败或被显式放弃时，撤销事务中已做的修改，使系统回到事务开始前的状态。
事务被创建之后，开始的一切行为可以被取消或回滚，举个例子，事务的创建API是CreateTransaction，基于该api进行CreateFile，并进行一系列操作，比如创建一个记事本写东西，都可以随时取消回滚，并且一切行为在普通用户看来是不会改变的，，除非提交
但如果你在事务下创建一个映射节，回滚事务之后，映射节的索引可能会丢失但映射节依然存在
