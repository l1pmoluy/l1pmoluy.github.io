6.改注册表

Appinit_DLL

该注册表项下的所有库都会被加载到所有加载 User32.dll 的进程中

因此，当恶意软件修改此子项时，大多数进程都会加载该恶意库

通过调用 RegCreateKeyEx 打开 Appinit_Dlls 注册表项，并通过调用 RegSetValueEx 修改其值

AppCertDlls

这种方法与 AppInit_DLLs 方法非常相似，区别在于此注册表项下的 DLL 会被加载到调用 Win32 API 函数 CreateProcess、CreateProcessAsUser、CreateProcessWithLogonW、CreateProcessWithTokenW 和 WinExec 的每个进程中

IFEO

IFEO 通常用于调试目的。开发人员可以设置此注册表项下的“调试器值”，将一个程序附加到另一个可执行文件进行调试。因此，每当启动可执行文件时，附加到该可执行文件的程序也会启动。要使用此功能，只需提供调试器的路径，并将其附加到要分析的可执行文件即可。恶意软件可以修改此注册表项，从而将自身注入到目标可执行文件中。

8.SETWINDOWLONG

确实不好懂，先要理解explorer(资源管理器)和命名共享节

命名共享节：(其实就是映射节)

一块可以使不同进程访问同一空间的手段，不过想要使两个进程都放到该空间的方法是要都映射过这个共享段

正常流程：

Explorer调用RegisterClassEx创建一个类（通常名为 "Shell_TrayWnd"）WNDCLASSEX，并设置好其内部的lpfnWndProc（类级的窗口过程指针）与cbClsExtra/cbWndExtra（类/窗口的额外内存，俗称 EWM），EWM 常用来放少量数据或回调表项

恶意流程：

先用MapViewFile将恶意文件映射在已经被explorer映射过的共享空间中，并将explorer中EWM的回调槽中存储的函数指针替换成共享段中的shellcode指针，这一过程可以通过GetWindowLong和SetWindowLong实现

看缺点之前插入一段很不错的知识

页属性共享涉及到操作系统的共享内存机制
这里简单描述一下： 为了节省内存，当一个模块加载进内存时，比如 ntdll.dll，操作系统会看该模块是否已被其他进程加载过了（即已经在物理内存中了）
如果在，那么操作系统只需要简单地将该物理区域映射到需要加载模块的进程中。
因此，这些模块对应的内存是共享的，这些模块内存对应的进程 pte (page table entry) 会指向一个叫 prototypePTE 的结构，该结构会指向这些共享的物理内存。
不过，如果我们向模块，比如 ntdll.dll，的数据段写入数据，那么这时操作系统就会对 ntdll.dll 的数据段分配一段物理内存，然后当前进程对应数据段的 pte 就不会再指向 prototypePTE，而是指向操作系统分配的物理内存。
关于内存共享机制的详细描述，读者看参考 Windows Internals 7th，第五章的 Page fault handling 部分。

缺点：

如果用UnMap，那么会被殊检查

如果不用，就要直接覆盖

覆盖如果不用ReMap自己实现，那么，进程对应pte不会指向protecctPTE，会被检测到

如果使用ReMap，需要一个section，那么文件就会落地

18.Attacking Worker Factories

流程：
GetQueryInformationProces()获得进程中的handle - DuplicateHandle()获得目标进程的worker factory - NtQueryInformationWorkerFactory()得到启动例程值 - 覆盖启动历程值 - NtSetWorkerFactoryInformation()增加一个线程来主动引起启动历程 - 实现注入

​

worker factory是windows负责管理线程池中的工作线程

启动例程是工作线程的入口点，而启动例程值可以被更改掉

19.Attacking Thread Pools

首先有一个工作项的概念，分为三种工作项

常规工作项、异步工作项(写入文件操作成功后)、定时工作项(定时器到点)

对应的有三种工作队列TP_POOL、I/O completion queue、定时器队列

主要关注前两个，TP_POOL位于进程内存空间的用户模式下，可以通过内存写入原句修改

I/O位于内核，要通过系统调用操作

TP_POOL中有TP_WORK结构，其辅助结构是TP_TASK，TP_TASK最终有ToPostTask API添加，由此得线程池结构

最后得到的流程就是：
得到进程信息 - 获取目标进程工厂和进程池信息 - 读一下TP_POOL - CreateThreadpoolWord创建一个工作项 - 创建并写入TP_WORK（shellcode的写入） - 连接TP_WORK和TP_POOL

20.Attacking Thread Pools: TP_IO

从这开始是一个体系，都是关于IO完成队列的，IO完成队列又可称为(IOCP)

结构降级: IOCP - KQUEUE - EntryList(链表结构，基础单元为 I/O completion entry)

IoCompletion结构其中一个值为

PVOID Key; // Completion Key

该结构为Completion Packet - 其中内容一般是 TP_WORK WP_WAIT等

通过NtSetIoCompletion函数可以向IOCP中插入一个IoCompletion

TP_IO是一个工作项，在文件操作完成后执行，TP_IO的辅助结构为TP_DIRECT，辅助结构就是将会在IOCP中排队的

CreateThreadpoolIo函数可以让一个TP_IO结构下的一个指针指向IOCP并使Completion key指向对应TP_DIRECT，类似于绑定TP_IO这个回调把

然后排队等待执行

流程:

得到进程信息确定进程工厂 - 打开一个文件 - CreateThreadpoolIo一个TP_IO(shellcode也在这里) - 远程开空间并写入 - NtSetIoCompletion插入TP_IO - 对文件简单操作后引发TP_IO

21-25 Attacking Thread Pools: TP_XX

也可以直接注入TP_DIRECT

1.从不同覆写API上分析

因为注入调用API是一致的，不一样的仅是几个单独覆写的API，所以可以从这方面入手分析

HijackHandle

未覆盖的是空函数，也就是没用到WorkerFactory信息

WorkerFactory方法需要具体的工厂信息

TP_WORK仅需要工厂句柄

TP_TIMER需要线程池句柄

AllocateShellcodeMemory

未覆盖的直接VirtualAllocEx创建，并返回地址

WorkerFacory返回启动例程地址，这也是他注入的核心

SetExecution

执行部分主要不同于每个方法的调用条件

WorkerFacory 手动设置最小运行线程是当前线程+1，工厂使用启动例程创建新线程的时候运行shellcode

TP_WORK 创建回调是shellcode工作项，远程写入并关联起来，是WORK工作项，当工作线程被调用自动回调

TP_WAIT 创建WAIT对象，远程写入WAIT和辅助项DIRECT，设置事件，绑定对象，触发回调

TP_IO 打开文件，创建IO对象，远程写入并绑定一个辅助项，写入文件触发回调

TP_DIRECT 这个最简洁，直接创建一个，回调绑上，跨进程写上，IOCP写里面

TP_TIMER 创建TIMER对象，远程写入并关联，通过w_NtSetTimer2开始计时，超时触发回调

总结：

注入技术这么看下来，都是在运行和不落地的方向进行优化

共享注入 Tran/Map/Proc主要的不断进化点在于，跨进程且不落地不用关键api的文件共享，注入就是想要实现两个进程的交互，那么至少目标进程要可以得到此运行进程的内容，在共享注入中，主要利用技术就是映射节，通过不断优化不落地，来躲避检测，而启动主要还是在利用ResumeThread或者CreateThread

而线程池注入主要倾向于如何让系统自然的运行代码，毕竟运行的逻辑是系统自然的
